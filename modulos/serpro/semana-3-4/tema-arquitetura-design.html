Frontend & Interfaces Responsivas
Single Page Application (SPA)

O navegador realiza o download de uma única página estrutural. A atualização de views e o fluxo de telas ocorrem via manipulação assíncrona do DOM (JSON manipulado por bibliotecas como React e VueJS), mitigando o reload completo do servidor.

Progressive Web App (PWA)

Estratégia que transforma aplicações web em experiências similares às nativas de dispositivos móveis. Utiliza Service Workers em segundo plano para interceptar requisições, permitindo cache agressivo, push notifications e funcionamento offline.

Integração, Gateway e Protocolos
API Gateway

Atua como o ponto único de entrada do ecossistema de microsserviços. É responsável por receber requisições externas, realizar a autenticação/autorização unificada e fazer o roteamento inteligente de tráfego para os serviços internos adequados.

RESTful vs GraphQL

O modelo REST baseia-se em recursos mapeados por URIs imutáveis acessadas via verbos HTTP estáveis. O GraphQL permite que o cliente envie uma query sob medida, solicitando apenas os campos desejados, o que erradica problemas de overfetching.

Microsserviços & Transações Distribuídas
Padrão SAGA

Responsável pela consistência de dados em transações que cruzam múltiplos microsserviços com bancos isolados. Executa uma série de transações locais em cadeia. Caso ocorra uma quebra ou rejeição em qualquer ponto intermediário, o padrão engatilha transações de compensação que desfazem os passos anteriores de forma reversa.

CQRS (Command Query Responsibility Segregation)

Segregação de Responsabilidade de Comando (Escrita/Alteração) e Consulta (Leitura). Cria caminhos ou até bancos de dados otimizados e distintos para operações de atualização de dados e operações de leitura rápida, permitindo escalabilidade assimétrica.

SOLID & Sustentabilidade de Código

Conjunto de boas práticas de engenharia de software fundamentais para o desenvolvimento limpo (Clean Code):

  • S (Single Responsibility): Uma classe deve reter apenas uma única responsabilidade central.
  • O (Open/Closed): O código deve ser aberto para extensão (herança/polimorfismo), mas totalmente fechado para modificação de fontes antigos.
  • L (Liskov Substitution): Classes filhas devem ser capazes de substituir suas classes mães perfeitamente sem quebrar o ecossistema.
  • I (Interface Segregation): Prefira múltiplas interfaces enxutas e focadas a uma única interface massiva e genérica.
  • D (Dependency Inversion): Módulos de alto nível não devem depender de detalhes de baixo nível; ambos devem depender de interfaces e abstrações.
Rasteira de Prova: O Cebraspe adora colocar exemplos de códigos que violam o princípio Open/Closed enchendo funções de blocos if/else ou switch para validar tipos de classes, quando o correto seria delegar o comportamento via polimorfismo dinâmico.
